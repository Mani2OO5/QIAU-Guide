### معرفی برنامه

هدف از نوشتن این برنامه، ایجاد یک چت‌بات تلگرامی مبتنی بر مدل زبانی است که بتواند بر اساس داده‌های دانشگاه، به سؤالات دانشجویان پاسخ دهد. در مورد اینکه این داده‌ها از کجا تهیه می‌شوند، کمی بعد توضیح می‌دهم.

در مرحله اول، ربات فقط به سؤالات متنی کاربران پاسخ می‌دهد. برای مثال، سؤالاتی مثل:

* «کلاس استاد X امروز برگزار می‌شود یا نه؟»
* «تاریخ انتخاب واحد یا حذف و اضافه چه زمانی است؟»
* «پرداخت به چه صورت انجام می‌شود؟»

اما اگر برنامه در آینده توسعه پیدا کند، انتظار می‌رود که بتواند با انواع مختلف فایل‌ها، مثل عکس، ویدیو و PDF نیز کار کند و بر اساس محتوای آن‌ها پاسخ تولید کند. حتی می‌توان از خود این فایل‌ها به‌عنوان پاسخ استفاده کرد. برای مثال، اگر کاربر بپرسد «برنامه درسی امروز چیست؟»، ربات می‌تواند تصویر برنامه درسی را برای او ارسال کند. طبیعتاً قابلیت‌های دیگری هم می‌توان در آینده به برنامه اضافه کرد.

### نحوه عملکرد برنامه

به‌صورت کلی، روند کار برنامه به این شکل است:

ابتدا داده‌های دانشگاه دریافت می‌شوند و با استفاده از یک مدل Embedding، از این داده‌ها یک دیتابیس وکتوری ساخته می‌شود.

سپس وقتی کاربر سؤالی می‌پرسد، پیام او توسط توابع تلگرامی دریافت می‌شود. متن پیام، به همراه تاریخ و ساعت ارسال آن، به مدل Embedding داده می‌شود و با استفاده از تکنیک RAG، نزدیک‌ترین اطلاعات مرتبط از دیتابیس وکتوری پیدا و برگردانده می‌شوند.

در مرحله بعد، اطلاعات پیدا شده به همراه سؤال کاربر و همچنین تاریخ و ساعت پیام، به مدل زبانی داده می‌شوند. در نهایت، مدل زبانی پاسخ نهایی را تولید می‌کند و این پاسخ از طریق توابع تلگرامی به‌صورت یک پیام برای کاربر ارسال می‌شود.

در طول این فرآیند، یک مدل زبانی دیگر نیز پیام‌های کاربر را بررسی می‌کند تا اگر کاربر اطلاعات مهمی مثل نام، شماره دانشجویی، شهر، رشته و موارد مشابه را وارد کرد، این اطلاعات را استخراج کند و به‌صورت یک Object در یک فایل JSON ذخیره کند.

برای هر کاربر، یک فایل JSON با نام User ID او ساخته می‌شود و اطلاعات مربوط به آن کاربر در این فایل ذخیره می‌شود.

البته ذخیره‌سازی تاریخچه چت بر عهده مدل زبانی دوم نیست و توابعی در فایل `main` این کار را انجام می‌دهند.

هدف از ذخیره تاریخچه چت این است که وقتی کاربر دوباره شروع به گفتگو می‌کند، مدل بتواند به مکالمات قبلی او دسترسی داشته باشد و بر اساس آن‌ها پاسخ مناسب‌تری تولید کند. برای جلوگیری از انباشته شدن بیش از حد تاریخچه و افزایش حجم اطلاعاتی که به مدل داده می‌شود، فقط ۲۰ پرسش و پاسخ آخر به مدل ارسال می‌شوند؛ اما کل تاریخچه به‌صورت کامل در فایل ذخیره می‌شود و در صورت نیاز قابل دسترسی است.

بدیهی است که هر دو مدل زبانی با استفاده از Prompt کنترل می‌شوند. به همین دلیل، دو System Prompt مختلف در برنامه داریم:

* `chat_prompt` برای مدلی که وظیفه تولید پاسخ نهایی را دارد.
* `info_prompt` برای مدلی که وظیفه استخراج و ذخیره اطلاعات کاربر را دارد.

طبق ساختار برنامه، مدل دوم همیشه خروجی خود را به‌صورت JSON تولید می‌کند.

این System Promptها شامل مجموعه‌ای از قوانین هستند که رفتار مدل را کنترل می‌کنند تا خروجی موردنظر برنامه تولید شود.

### مشکلات و محدودیت‌ها

اولین مشکلی که با آن مواجه شدم، مربوط به تهیه داده‌های دانشگاه آزاد بود.

در ابتدا تصمیم داشتم از اطلاعات موجود در سایت دانشگاه آزاد قزوین استفاده کنم، اما بعد از بررسی سایت متوجه شدم که بسیاری از بخش‌های آن مدت زیادی است که به‌روزرسانی نشده‌اند و اطلاعات قابل استفاده و به‌روزی در آن وجود ندارد.

در نهایت تصمیم گرفتم از پیام‌های کانال جزوه استفاده کنم.

یک بار تمام پیام‌های کانال جزوه را Export گرفتم و با استفاده از آن‌ها دیتابیس وکتوری را ساختم. از آن به بعد نیز هر چند روز یک‌بار پیام‌های جدید را Export می‌کنم و دیتابیس را به‌روزرسانی می‌کنم.

حالت ایده‌آل این است که فرآیند:

`Export Data → Update Database`

به‌صورت خودکار انجام شود؛ برای مثال، هر ساعت یا هر زمان که پیام جدیدی در کانال منتشر شد.

اما برای انجام خودکار این فرآیند، به Telegram API ID و API Hash نیاز دارم که در حال حاضر نتوانستم آن‌ها را از سایت تلگرام دریافت کنم.

### نسخه‌های مختلف برنامه

من برنامه را در دو محیط مختلف توسعه داده‌ام؛ یکی با Ollama و دیگری با Gemini. به همین دلیل اگر در حال حاضر صفحه پروژه را در GitHub مشاهده کنید، سه شاخه مختلف در آن وجود دارد.

شاخه اول، `gemini` است. در این نسخه، برنامه با استفاده از Gemini API اجرا می‌شود و هم مدل زبانی و هم مدل Embedding از سرویس Gemini استفاده می‌کنند.

این نسخه در تست‌هایی که انجام دادم، خروجی باکیفیتی دارد، خطای کمی دارد و سرعت آن نیز مناسب است. در مجموع، از نظر عملکرد، این نسخه برای من خروجی مطلوب‌تری داشته است.

شاخه دوم، `ollama` است. در این نسخه، مدل زبانی و مدل Embedding به‌صورت Local و با استفاده از Ollama اجرا می‌شوند.

مزیت اصلی این روش، نداشتن هزینه API است. اما به دلیل محدودیت سخت‌افزاری سیستم، مجبور شدم از مدل‌های بسیار سبک استفاده کنم. این مدل‌ها، مخصوصاً در زبان فارسی، عملکرد مطلوبی ندارند و در بسیاری از مواقع خروجی مناسبی تولید نمی‌کنند.

شاخه سوم نیز `main` است که شاخه اصلی توسعه برنامه محسوب می‌شود و در حال حاضر محتوای آن تفاوتی با نسخه Ollama ندارد.

### محدودیت‌های Ollama و Gemini

در واقع، هم نسخه Ollama و هم نسخه Gemini محدودیت‌هایی دارند که روی عملکرد نهایی برنامه تأثیر می‌گذارند.

همان‌طور که گفتم، برای استفاده از Ollama به دلیل محدودیت سخت‌افزاری، مجبور شدم از مدل‌های بسیار سبک استفاده کنم. با وجود سبک بودن این مدل‌ها، اجرای برنامه همچنان نسبتاً کند است و علاوه بر آن، به دلیل ضعف مدل‌های انتخاب‌شده در پردازش زبان فارسی، خروجی همیشه مطلوب نیست.

اما نکته مهم این است که ساختار خود برنامه درست است و برنامه بدون مشکل اجرا می‌شود. طبیعتاً اگر برنامه روی سیستم قدرتمندتری اجرا شود و از مدل‌های سنگین‌تر و مناسب‌تری استفاده شود، می‌توان خروجی بسیار بهتری دریافت کرد.

همچنین تغییر مدل در ساختار فعلی برنامه کار پیچیده‌ای نیست و با تغییر یک متغیر می‌توان مدل مورد استفاده را عوض کرد و نیازی به تغییر ساختار اصلی برنامه وجود ندارد.

در مورد نسخه Gemini نیز مشکل اصلی هزینه API است. این نسخه در تست‌هایی که انجام دادم خروجی بسیار خوبی دارد، اما استفاده مداوم از API هزینه‌بر است و برای یک پروژه کوچک، پرداخت هزینه زیاد برای API منطقی نبود.

با این حال، ساختار این نسخه نیز کاملاً آماده است و تنها با قرار دادن یک API Key می‌توان آن را اجرا کرد.

در واقع، می‌توان گفت این نسخه مثل ماشینی است که ساخته شده، اما در حال حاضر کلید آن را نداریم! :D
